# Memo writing guide

This guide is intended for AI agents to read and follow whenever they create, edit, or rename memos in this project. Treat it as working instructions, while giving the user’s explicit requests precedence.

## 000 — Background

Memos preserve useful explanations, discussion outcomes, and agreed decisions for TDS. This is the authoritative guide for memo naming, structure, style, backups, and pictures; [memo 005](memoWX_005_informationWorkflow.md) covers source extraction, evidence checks, and knowledge continuity. `AGENTS.md` directs agents here rather than duplicating these rules.

## 001 — Names and indexing

Use `memo<author>_<NNN>_<descriptiveTitle>.md`, for example `memoWX_006_memoWritingGuide.md`. Keep underscores between the author prefix, three-digit number, and title. WX and KWX have separate number sequences.

Before creating a memo, check [the index](README.md) and the files in this directory. Use the next unused number in the author's sequence; the next numbers after this update are WX `007` and KWX `002`. Treat those as starting points, and check again before assigning a number.

Keep existing numbers stable when editing a memo, and do not reuse a number for a different topic. Add each new memo to the index; when a filename changes, update its index entry and any links that refer to it. Do not rename existing memos merely to normalize spelling or title style.

## 002 — Sections and structure

Start with one clear document title. Use three-digit section numbers in order: `## 000 — Background`, `## 001 — …`, `## 002 — …`. Use ordinary unnumbered subheadings when a section needs smaller parts.

Section 000 gives the context, purpose, and scope in a short paragraph. Section 001 gives the main explanation, overview, or current decision; later sections develop the details. Choose section titles for the topic rather than forcing every memo into the same outline.

For a folder memo, use 000 for background, 001 for the annotated tree and summary, and 002 for detailed explanations. Put a short description beside each folder in the tree, then explain each folder in two or three sentences below it. Expand individual concepts further when the user requests more detail.

## 003 — Writing style

Use plain language and explain unfamiliar terms before relying on them. Introduce the concrete object, explain its purpose, and give an example when that makes the idea clearer. Keep paragraphs focused and avoid repeating the same explanation in several sections.

Match the user's requested language and level of detail. Use prose for explanations, lists for parallel items or steps, and tables for comparisons. Keep source code, concepts, experiments, and documentation clearly distinguished when explaining project structure.

## 004 — Evidence and decisions

Distinguish observed facts, source claims, interpretations, proposals, and agreed decisions in the wording. Check the relevant files before describing the current implementation, and record the inspection date when the description may become stale. Label future folders and designs as proposals.

Link sources close to the claims they support and retain important conditions or limitations when summarizing. Prefer repository-relative links so the memo works across machines. Preserve original reference material and user-written notes unless the user asks to revise them.

## 005 — Updating and checking

Update the existing memo when continuing the same topic; create a new memo for a separate subject that needs its own reference. Preserve useful reasoning and current decisions, and revise only the scope requested by the user. The user's explicit instructions take precedence over this guide.

Before finishing, check the filename and index entry, section numbering, relative links, and consistency with the actual project. Read the edited text once for clarity and unnecessary repetition. Do not add a skill or extra workflow unless the user asks for it or repeated use establishes a need.


## 006 — Back up before every modification

Before modifying an existing memo, save a complete copy of its current contents in `docs/memo/backups/`. Name the backup `<originalStem>__YYYYMMDD_HHMMSS_microseconds.md`, using America/Los_Angeles time, and never overwrite an earlier backup. This rule also applies to this writing guide and to renaming a memo; creating a brand-new memo does not require a backup.

Make the backup before each edit operation, then modify the active memo. Keep backups unchanged and out of the active memo numbering and index; they preserve earlier versions rather than introduce new topics. If the backup cannot be saved, leave the memo unchanged and report the problem.


## 007 — Pictures belong beside their memo

Save a memo's pictures in a sibling folder with exactly the same name as the memo file, excluding `.md`. Copy or derive illustrations without moving or overwriting original reference material. For example, `docs/memo/memoWX_002_MAS.md` uses `docs/memo/memoWX_002_MAS/` for its pictures. Create the folder when the memo first needs an image, and use clear filenames inside it.

Embed pictures with relative paths, for example `![System overview](memoWX_002_MAS/system-overview.png)`. Keep the image files with the memo when sharing or moving it; when renaming a memo, rename its picture folder and update the image links as well. Before replacing or deleting a picture, preserve its existing version under `docs/memo/backups/` in a timestamped folder named after the memo so earlier content can be recovered.
