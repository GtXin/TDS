### Quote 02 — 包含定义与向上／向下合并规则

第62课，正文，本地源文件第38行。[1]

> 当然，实际图形里，有些复杂的关系会出现，就是相邻两K线可以出现如图6这种包含关系，也就是一K线的高低点全在另一K线的范围里，这种情况下，可以这样处理，在向上时，把两K线的最高点当高点，而两K线低点中的较高者当成低点，这样就把两K线合并成一新的K线；反之，当向下时，把两K线的最低点当低点，而两K线高点中的较低者当成高点，这样就把两K线合并成一新的K线。经过这样的处理，所有K线图都可以处理成没有包含关系的图形。

### Quote 03 — 连续包含组的等价区间

第65课，正文，本地源文件第31行。[2]

> 1、用[di,gi]记号第i根K线的最低和最高构成的区间，当向上时，顺次n个包含关系的K线组，等价于[maxdi,maxgi]的区间对应的K线，也就是说，这n个K线，和最低最高的区间为[maxdi,maxgi]的K线是一回事情；向下时，顺次n个包含关系的K线组，等价于[mindi,mingi]的区间对应的K线。

### Quote 04 — 不满足传递律，必须顺序合并

第65课，正文，本地源文件第33行。[2]

> 2、结合律是有关本ID这理论中最基础的，在K线的包含关系中，当然也需要遵守，而包含关系，不符合传递律，也就是说，第1、2根K线是包含关系，第2、3根也是包含关系，但并不意味着第1、3根就有包含关系。因此在K线包含关系的分析中，还要遵守顺序原则，就是先用第1、2根K线的包含关系确认新的K线，然后用新的K线去和第三根比，如果有包含关系，继续用包含关系的法则结合成新的K线，如果没有，就按正常K线去处理。

### Quote 05 — 合并方向的前置条件与判定

第65课，正文，本地源文件第37行。[2]

> 假设，第n根K线满足第n根与第n+1根的包含关系，而第n根与第n-1根不是包含关系，那么如果gn>=gn-1，那么称第n-1、n、n+1根K线是向上的；如果dn<=dn-1，那么称第n-1、n、n+1根K线是向下的。

## Appendix B — CC 的K线包含处理：按代码梳理

依据下载网站中的 `KlineCombiner` 可执行语句整理，核对日期：2026-11-08。源码使用 `manual_rebuild` 命名空间；以下描述该网站版本的实现，不以网站解释文字代替代码，也不直接作为TDS已确认算法。[8]

### B.1 — 状态与输入

`append(k)` 每次接收一根K线。`_lead` 保存尚未定向的前导原始K线，`_units` 保存合并单元，`_established` 标记是否已经定向，`_total` 给出下一根的原始索引。每个单元保存 `high/low/dir/start_index/members`。合并计算只读取高低点，不按阴阳线或收盘涨跌定向。[8]

### B.2 — 启动：先等方向，再合并前导组

1. 未定向时，先把新K线加入 `_lead`；不足两根则等待。
2. `_try_establish()` 只比较前导缓冲最后两根**原始K线**。`_direction(a,b)` 要求 `b.high > a.high` 且 `b.low > a.low` 才向上；两者都严格小于才向下；否则继续等待。
3. 首次得到方向 `d` 后，取 `_lead[:-1]` 为 `blob`。`_merge_blob()` 按 `d` 将整个前导组聚合：向上分别取全部成员的 `max(high)`、`max(low)`；向下分别取 `min(high)`、`min(low)`。
4. 前导组成为首单元；触发定向的最后一根单独成为第二单元。清空 `_lead`，进入常规追加阶段。[8]

**代码启示：** 前导方向来自后出现的第一个严格同向高低点对，随后用于解释此前的包含链；这是CC的初始化选择。若整个输入窗口始终无法定向，`_units` 保持空，`to_merged_klines()` 返回空列表。启动阶段直接聚合前导组，常规阶段才逐根与末端合并单元比较，两条路径应分开理解。[8]

### B.3 — 常规追加：先判包含，再决定合并或新建

令 `a` 为 `_units[-1]`、`b` 为新K线。`_contains(a,b)` 的实际条件为 `a.high >= b.high and a.low <= b.low`；调用处再用 `or _contains(b,a)` 检查反向包含，所以边界相等也参与包含判断。[8]

| 分支 | 实际动作 | 方向 |
|---|---|---|
| 互含，末单元向上 | `high = max(a.high, b.high)`；`low = max(a.low, b.low)`；将b加入 `members` | 保留末单元方向 |
| 互含，末单元向下 | `high = min(a.high, b.high)`；`low = min(a.low, b.low)`；将b加入 `members` | 保留末单元方向 |
| 不互含 | 用末单元的当前高低点与b调用 `_direction()`，新建单元 | 新方向可延续或反转 |

**代码启示：** 比较对象是已经合并后的末单元，不是上一根原始K线；包含分支不重新定向。代码使用直接浮点比较，没有容差或近似相等参数。[8]

### B.4 — 末根更新：撤回旧值，再追加新值

`pop_last_kline()` 撤销最近一根：前导阶段直接弹出 `_lead`；定向后先从末单元移除成员，若还有成员则 `_recompute_unit()` 按原方向重算高低点，空单元则删除。如果撤回的正是建立初始方向的K线，使结果只剩 `merge.init` 单元，代码将其成员放回 `_lead`，清空单元并恢复未定向状态。调用方随后 `append()` 新值；时间戳顺序由上游保证，本类的 `append()` 没有自行校验。[8]

### B.5 — 输出与可追溯性

`to_merged_klines()` 输出方向、高低点、成员首尾时间戳与原始起止索引；`end_index = start_index + len(members) - 1`，依赖输入顺序及成员连续。`StructTrace` 保存算法卡ID、规则ID及来源时间范围。`_derive_rule_id()` 优先保留首单元的 `merge.init`；其他单元多成员时输出 `merge.contains`，单成员时输出形成方向的规则ID。[8]

`stable_index()` 返回倒数第二单元的原始结束索引，不足两个单元返回 `-1`。这表达正常追加下最后单元仍可改变；显式撤回可跨过初始化边界，因此不应把此稳定点理解为任意回退后的永久承诺。[8]

### B.6 — 阅读边界

以上为网站代码的静态检查结果，未运行完整CC引擎。值得后续核验的是：前导聚合与常规顺序合并的边界、全包含窗口的空输出、相等极值及同时间戳更新时的回退。它们属于实现行为和待验证事项，不补写为Chan原文规则。[8]
