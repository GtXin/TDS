# Chan_fenxing

## 000 — Scope

## 001 — Definition (What)

(版本一) MergedKline序列中，k线的高低值必然同时单调递增或者单调递减。单调递增变递减的拐点k线为顶分型；反之为底分型。

（版本二）在已完成包含处理、相邻K线之间不存在包含关系的 MergedKline 序列中，每对相邻K线的高点与低点均同向严格递增或严格递减。连续三根K线中，若前两根到后两根的变化方向由上升转为下降，则这三根K线构成顶分型；由下降转为上升，则构成底分型。中间K线为分型的中心K线，其高点为顶分型的顶，其低点为底分型的底。
## 002 — Algorithm (How)

### 002.a — Algorithm Tree

按001版本二，在完整且校验通过的MergedKlineSeries上逐窗识别全部几何分型。字段沿用[memo009](memoWX_009_designPatternForChanFeatures.md#002f--fenxing)，输入沿用[memo026](memoWX_026_MergedKlineFamily.md#003c--mergedklineseries)。以下为算法设计；笔的端点取舍留给笔层。

**变量与位置**

| 变量 | 含义与约定 |
|---|---|
| `merged` | 输入的确切MergedKlineSeries对象；记录位于 `merged.klines`，不修改输入。 |
| `raw` | `merged.source_series`，同一个不可变KlineTSeries。 |
| `N` | 合并单元数，即 `len(merged)`；有效完整序列至少有1根。 |
| `i` | 本轮中心合并单元的零基下标，从1开始，最后可检查到N−2。 |
| `A、B、C` | `merged[i−1]、merged[i]、merged[i+1]`；B为中心，不是 `raw[i]`。 |
| `d_left、d_right` | 根据高低点重新计算的A→B、B→C方向；不直接读取单元的direction。 |
| `R` | 已保存分型的工作列表；最终冻结为FenxingSeries.items。 |
| `T、P` | 本层执行依据列表、每条分型对应的trace下标元组列表；最终分别冻结为trace、trace_by_point。 |
| `next_id` | 本次分型结果的下一个整数ID，从0开始；仅保存成功时增加，不等于i或MergedKline.id。 |
| `J` | 中心B的原始成员中，与price对应的原始下标集合；只作逻辑记号，实际累计匹配数量及首尾下标。 |

每次进入2.3时，小于i的完整中心均已检查，R恰好包含这些中心检出的分型；`len(R)=len(P)=next_id`。source_start／source_stop必须结合所属对象理解：MergedKline指向raw，Fenxing指向merged，均为左闭右开范围。

**判断树：判断结果 → 行动 → 下一步**

```text
2.1 输入与规则检查
├── 2.1.a 输入不是完整MergedKlineSeries，或校验失败
│   → 报错，停止；不能把待定、双路包装或无效输入当成空分型结果
└── 2.1.b 输入校验通过
    → merged=source_series；raw=merged.source_series；
      检查本层config及非空的规则位置／版本rule_tree_ref；
      规则选项无效则报错，不修改上游；
      N=len(merged)；R、T、P为空；next_id=0；i=1
    └── 2.2 合并单元数量检查
        ├── 2.2.a N<3
        │   → 记录“没有完整三根窗口”；转2.8组装空结果
        └── 2.2.b N≥3
            → 转2.3

2.3 中心位置检查
├── 2.3.a i≥N−1，完整窗口已耗尽
│   → 转2.8；不读取merged[N]，不为末根补造分型
└── 2.3.b i<N−1，仍有完整窗口
    → A=merged[i−1]；B=merged[i]；C=merged[i+1]
    └── 2.4 相邻区间方向检查
        → 由A、B计算d_left；由B、C计算d_right
        ├── 任一对不能得到严格向上或严格向下
        │   → 报错，指出对应位置；不能作为普通“无分型”跳过
        └── 两对方向均有效
            └── 2.5 三根结构分类
                ├── 2.5.a 向上→向下
                │   → 顶分型：kind="top"；price=B.high；转2.6
                ├── 2.5.b 向下→向上
                │   → 底分型：kind="bottom"；price=B.low；转2.6
                ├── 2.5.c 向上→向上
                │   → 连续上升，不保存分型；记录判断依据，转2.7
                └── 2.5.d 向下→向下
                    → 连续下降，不保存分型；记录判断依据，转2.7

2.6 定位原始锚点并保存
→ 只遍历原始下标j∈[B.source_start,B.source_stop)，逐项读取raw[j]，不创建切片；
  顶分型以原始high=price匹配，底分型以原始low=price匹配，得到J
├── 2.6.a J为空
│   → 分型价格与原始来源不一致，报错停止
├── 2.6.b J只有一个下标
│   → anchor_raw_index取该下标；转2.6.d
└── 2.6.c J有多个下标
    ├── 默认最早匹配 → anchor_raw_index=min(J)；转2.6.d
    └── config明确选择最晚匹配 → anchor_raw_index=max(J)；转2.6.d

2.6.d 保存本轮Fenxing
→ id=next_id；kind、price沿用2.5；
  source_start=i−1；source_stop=i+2；
  anchor_raw_index沿用2.6；status="unconfirmed"；confirmed_at=None；
  保存本轮分类／锚点依据到T，构造并校验不可变Fenxing，追加到R；
  将其相关trace下标元组追加到P；next_id=next_id+1；转2.7

2.7 推进窗口
→ i=i+1；回2.3；有分型、无分型都只前进一根

2.8 组装并校验结果
→ FenxingSeries.source_series=merged；items=tuple(R)；
  保存本层config、rule_tree_ref；trace=tuple(T)；trace_by_point=tuple(P)；
  冻结嵌套配置与依据数据，校验通过后返回；失败则报错
```

**必要约定与校验**

1. 相邻区间high、low都严格升高为向上，都严格降低为向下；方向由本轮价格计算，不借用单元的direction。等边或高低点反向变化应报错。
2. 同价锚点默认取最早匹配，config可显式改为最晚匹配；实际采用的策略记入config。按原始精度严格匹配，不临时取整或加容差。上游校验不复算全部合并价格，因此仍须检查J为空的来源异常。
3. 返回前检查确切source_series引用、唯一整数ID、窗口长度为3、中心顺序及原始锚点与价格一致；窗口允许重叠。MergedKline的来源下标指向raw，Fenxing的来源下标指向merged，均为左闭右开范围。
4. trace保留每个完整窗口的判断，包括无分型分支。trace_by_point与items等长，每条分型对应非空且有效的trace下标元组；空items可有非空trace，无须让每条trace都关联输出。具体DecisionStep结构仍待定义。

### 002.b — Detailed Implementation logic and Numerical Examples

本节直接从已处理好的MergedKlineSeries开始。价格区间写作 `[low,high]`，来源范围写作 `[start,stop)`；数值为教学构造，分型按四项严格比较核算。

#### 处理逻辑

1. **准备（2.1–2.2）。** 校验完整merged，保留其确切引用；同价锚点默认FIRST（最早），显式LAST取最晚。初始化R、T、P和ID；不足三根则记录原因并返回空结果。
2. **读取三根（2.3–2.4）。** 中心i从1到N−2，取A、B、C，按本轮high／low计算左右方向；仍有包含或等边则报错。
3. **分类（2.5）。** 上→下为顶，price=B.high；下→上为底，price=B.low；同向则不保存分型，但保留判断依据。
4. **定位并保存（2.6）。** 只在B的原始成员中匹配顶的high或底的low；没有匹配报错，有匹配按FIRST／LAST定位。保存8个Fenxing字段及相关依据。
5. **推进（2.7）。** 每轮i只增加1，不能因检出分型而跳过后面的窗口；ID只在保存成功时增加。
6. **结束（2.8）。** 冻结并组装6成员FenxingSeries，校验来源、全部应有结果和trace映射；不额外保存末根，不自动确认。

#### 主例：7个已处理单元 → 3个分型

给定以下序列。M0–M6表示merged位置；原始来源范围只用于定位分型锚点。

| merged位置 | 价格区间 | 原始来源范围 |
|---|---|---|
| M0 | `[0,3]` | `[0,1)` |
| M1 | `[3,6]` | `[1,4)` |
| M2 | `[1,4]` | `[4,5)` |
| M3 | `[0,2]` | `[5,7)` |
| M4 | `[2,5]` | `[7,8)` |
| M5 | `[3,6]` | `[8,9)` |
| M6 | `[1,4]` | `[9,10)` |

| 中心i | 左／右方向 | 分支与结果 | 分型merged窗口 | 原始锚点匹配J | 默认锚点 |
|---|---|---|---|---|---|
| 1 | up／down | 2.5.a：FX0，顶，price=6 | `[0,3)` | `{2,3}` | 2 |
| 2 | down／down | 2.5.d：无分型 | — | — | — |
| 3 | down／up | 2.5.b：FX1，底，price=0 | `[2,5)` | `{5,6}` | 5 |
| 4 | up／up | 2.5.c：无分型 | — | — | — |
| 5 | up／down | 2.5.a：FX2，顶，price=6 | `[4,7)` | `{8}` | 8 |

i=1的四项为 `6>3、6>4、3>0、3>1`；i=3为 `0<1、0<2、2<4、2<5`。FX0与FX1共享M2，FX1与FX2共享M4，仍全部保存；本层不进行笔端点取舍。

![给定处理后序列中的分型判断](memoWX_019_Chan_fenxing/fractal-window-example.png)

图中横轴是merged位置，矩形仅表示high／low区间；分型标记位于中心M1、M3、M5，实际原始锚点下标另见标签和表格。等间距不表示原始时间跨度。

**同价锚点。** M1的原始成员中，raw1.high=5、raw2.high=raw3.high=6，因此默认FIRST取raw2，显式LAST取raw3。M3的raw5.low=raw6.low=0，相应取raw5或raw6。三条记录的price、kind和merged窗口不变，只有前两条的原始锚点改变。

默认结果的3条记录均为 `status="unconfirmed"、confirmed_at=None`；ID为0、1、2。本例伪代码每窗记录一条依据，因此trace有5条，`trace_by_point=((0,),(2,),(4,))`；两条无分型依据仍留在trace中。

#### 边界与末端修订

| 场景 | 应有处理 |
|---|---|
| 只有1或2个有效合并单元 | 空items、空trace_by_point；trace记录不足三根。 |
| `[1,3]→[2,4]→[3,5]`，或完全反向 | 检查1个窗口但无分型；trace保留同向判断。 |
| 手工输入相邻 `[1,5]、[3,5]` | 等高构成包含，输入校验拒绝，不能当作普通无分型。 |
| 手工把主例M1.high改成7，其余不变 | 结构校验可能通过，但raw1–3中没有high=7；J为空，报来源异常。 |
| config缺少同价策略 | 采用并记录FIRST；非法策略或未知选项报错。 |

将给定末单元M6从 `[1,4]` 修订为 `[4,7]`，其来源raw9的high同步为7。重新扫描后，原中心i=5变为连续上升，旧FX2消失；M6仍无右邻，不能自己形成新顶。

再给定M7=`[2,5]`，来源范围 `[10,11)`：新中心i=6构成顶，price=7、anchor_raw_index=9、merged窗口 `[5,8)`。新顶标在raw9，但要有右邻M7才具备三根判断依据；这不等于已经定义确认时间。不同结果版本可重用整数ID，新旧FX2不是同一个结果对象。

### 002.c — Helper Functions

以下5个拟议辅助函数均为FenxingSeries的私有方法，不新增类或修改原始数据。入口复用现有 `merged.validate()`；主循环负责i、ID、R、T、P和结果组装。具体DecisionStep结构仍不在本节定义。

#### 规范化本层配置：_normalize_config

**接口：** `_normalize_config(config)`。

config为映射；本版仅接受可选键 `anchor_tie`，值为FIRST或LAST。缺少该键时补FIRST；未知键、None或非法值报错，不以默认值掩盖错误。返回独立、不可变的有效配置，例如 `{"anchor_tie":"FIRST"}`；不修改调用方或上游merged.config。

#### 判断相邻方向：_direction_between

**接口：** `_direction_between(a, b)`；a在前、b在后。

输入已校验、按来源相邻的两个合并单元。b的high、low均严格较大返回up，均严格较小返回down；其余关系报错。函数不读取或覆盖单元direction，不设价格容差，不推进扫描位置。

#### 分类三根窗口：_classify_window

**接口：** `_classify_window(a, b, c)`。

调用_direction_between得到左右方向，返回普通数据元组 `(kind, price, d_left, d_right)`。up／down返回 `(top,b.high,up,down)`；down／up返回 `(bottom,b.low,down,up)`；两种同向情况的kind、price均为None，仍返回方向供trace使用。函数不定位原始锚点、不构造Fenxing。

#### 定位原始锚点：_resolve_anchor

**接口：** `_resolve_anchor(raw, center, kind, price, policy)`。

raw必须是当前merged的确切原始来源；center来自当前窗口，要求 `0≤source_start<source_stop≤len(raw)`。kind为top／bottom，price分别等于center.high／low，policy必须为已规范化的FIRST／LAST。

按原始下标递增遍历center来源范围：顶比较raw[j].high，底比较raw[j].low，使用严格相等。只累计匹配数量、首个及最后匹配下标，不创建raw切片或完整匹配列表。没有匹配报错；否则返回 `(anchor_raw_index, count, first, last)`，其中锚点按policy取first或last。即使FIRST已经找到，也完成本组扫描，以保存完整匹配数量和首尾依据。

#### 校验本层完整结果：_validate_result

**接口：** `_validate_result(merged, result)`。

这是拟议 `FenxingSeries.validate()` 的本层校验核心；不再次调用result.validate，避免递归。merged已通过入口校验，本函数不重跑上游合并。

1. 检查确切source_series引用、有效配置（已含anchor_tie）／规则版本、8字段记录的局部合法性、唯一整数ID及unconfirmed／None。窗口必须有3根且在merged范围内；原始锚点位于中心原始范围。
2. 按i=1…N−2顺序重检窗口，用一个结果指针逐项核对全部应有分型、kind、price和窗口，拒绝漏报、误报、多报及乱序；每次命中再用_resolve_anchor核对选定锚点。允许窗口重叠，不要求分型覆盖全部原始K线。
3. 本伪代码每个完整窗口恰有一条逻辑依据，按中心顺序核对数量与内容，拒绝缺失、重复或虚假事件；不足三根时恰有一条原因依据。trace_by_point与items等长，每条结果关联自己的窗口依据，并复核匹配数量、首尾、所选锚点和策略；无输出依据无需关联结果。

成功返回None，失败报错；不排序、不修补、不分配新ID。记录构造校验局部字段，序列构造自动执行本层完整校验；主循环不再重复校验刚构造好的序列。

### 002.d — Pseudocode

以下是算法伪代码，不是已实现的Python接口。使用002.c的5个私有辅助函数；“记录依据”表示保存本轮实际比较及来源的逻辑动作，不规定DecisionStep的新字段。

#### 主过程

```text
FenxingSeries.derive_from(source_series, config, rule_tree_ref):
    若source_series不是完整MergedKlineSeries：报错
    merged ← source_series
    merged.validate()
    若rule_tree_ref不是非空规则位置／版本：报错
    effective ← _normalize_config(config)       # 缺省anchor_tie=FIRST
    raw ← merged.source_series
    N ← len(merged)
    R、T、P ← 三个独立空列表
    next_id ← 0
    i ← 1

    若N<3：
        将“不足三根”的来源依据追加到T

    当i<N−1时重复：
        断言len(R)=len(P)=next_id
        A ← merged[i−1]
        B ← merged[i]
        C ← merged[i+1]
        kind, price, left, right ← _classify_window(A, B, C)
        anchor_evidence ← None

        若kind不是None：
            anchor, count, first, last ← _resolve_anchor(
                raw, B, kind, price, effective["anchor_tie"])
            anchor_evidence ← 所选锚点、数量、首尾匹配及实际策略

        e ← len(T)
        将本轮i、窗口、来源、左右方向、kind、price及anchor_evidence追加到T

        若kind不是None：
            point ← Fenxing(
                id=next_id, kind=kind, price=price,
                anchor_raw_index=anchor,
                source_start=i−1, source_stop=i+2,
                status="unconfirmed", confirmed_at=None)
            将point追加到R                   # 构造时校验局部字段
            将(e,)追加到P
            next_id ← next_id+1

        i ← i+1                            # 包括无分型分支

    返回FenxingSeries(
        source_series=merged,
        items=tuple(R), config=effective, rule_tree_ref=rule_tree_ref,
        trace=T的深度不可变副本, trace_by_point=tuple(P))
        # 构造时自动调用validate → _validate_result；失败则报错
```

#### 原始锚点扫描

```text
_resolve_anchor(raw, center, kind, price, policy):
    检查002.c规定的范围、kind、price与policy前提
    count ← 0
    first、last ← None
    对j从center.source_start到center.source_stop−1：
        value ← raw[j].high（top）或raw[j].low（bottom）
        若value=price：
            若first为None：first ← j
            last ← j
            count ← count+1
    若count=0：报来源异常
    anchor ← first（FIRST）或last（LAST）
    返回(anchor, count, first, last)
```

#### 完整性校验的顺序

```text
_validate_result(merged, result):
    检查002.c的引用、配置、局部字段和trace映射长度
    若len(merged)<3：
        检查items及trace_by_point为空，trace恰有一条对应“不足三根”的依据
        返回None
    检查len(result.trace)=len(merged)−2
    p ← 0                                  # 结果位置，不是特征ID
    对i从1到len(merged)−2：
        kind, price, left, right ← _classify_window(
            merged[i−1], merged[i], merged[i+1])
        e ← i−1
        核对result.trace[e]的中心、窗口、方向、kind及price与本轮一致
        若kind为None：
            检查该依据没有锚点记录；继续下一中心
        若p=len(result.items)：报漏报
        point ← result.items[p]
        核对point的kind、price及窗口[i−1,i+2)
        anchor, count, first, last ← _resolve_anchor(
            merged.source_series, merged[i], kind, price, result.config["anchor_tie"])
        核对point.anchor_raw_index，以及依据中的count、first、last和实际策略
        检查result.trace_by_point[p]=(e,)
        p ← p+1
    若p≠len(result.items)：报多报／乱序
    返回None
```

### A.6 — 第82课：三次较量、力度与中继

正文26–54行。[6] 保留“分型不是分形”、三根K线的心理解释及两个原图；原文“几乎100%”等措辞仅是作者论述，本附录未作统计验证。36行`娇注`以及48行归属未明的“注”按整理本标识保留，不升级为作者规则。

> 走势反映的是人的贪嗔痴疑慢，如果你能通过走势当下的呈现，而观照其中参与的心理呈现，就等于看穿了市场参与者的内心。心理，不是虚无飘渺的，最终必然要留下痕迹，也就是市场走势本身。而一些具有自相似性的结构，就正好是窥测市场心理的科学仪器。
>
> 注意，分型不是分形，分形理论，是数学的一个分支，有人用这分支的一些研究成果硬套到市场走势上，得出来的结论，没有太大意义。本ID理论的逻辑，是直接来源于市场走势本身，而不是一个先验的，市场之外的数学理论。至于这现实的市场逻辑显现出数学理论的结构，那是另一回事情。
>
> 世界，本来就是数学的。但本ID的理论，不是任何原有数学理论的应用，而是市场本身现实逻辑的直接显现，这是一个极为关键的区别。
>
> 显然，一个顶分型之所以成立，是卖的分力最终战胜了买的分力，而其中，买的分力有三次的努力，而卖的分力，有三次的阻击。用最标准的已经过包含处理的三K线模型：第一根K线的高点，被卖分力阻击后，出现回落，这个回落，出现在第一根K线的上影部分或者第二根K线的下影部分，而在第二根K线，出现一个更高的高点，但这个高点，显然与第一根K线的高点中出现的买的分力，一定在小级别上出现力度背驰，从而至少制造了第二根K线的上影部分。最后，第三根K线，会再次继续一次买的分力的攻击，但这个攻击，完全被卖的分力击败，从而不能成为一个新高点，在小级别上，大致出现一种第二类卖点的走势。
>
> 由上可见，一个分型结构的出现，如同中枢，都是经过一个三次的反复心理较量过程，只是中枢用的是三个次级别。所谓一而再、再而三，三而竭，所以一个顶分型就这样出现了，而底分型的情况，反过来就是。
>
> 现在，我们可以深入分析这三根K线的不同情况。首先，一个完全没有包含关系的分型结构，意味着市场双方都是直截了当，没有太多犹豫。包含关系（娇注：只要不是直接把阳线以长阴线吃掉）意味着一种犹豫，一种不确定的观望等，一般在小级别上，都会有中枢延伸、扩展之类的东西。
>
> 其次，还是用没有包含关系的顶分型为例子。**如果第一K线是一长阳线，而第二、三都是小阴、小阳，那么这个分型结构的意义就不大了**，在小级别上，一定显现出小级别中枢上移后小级别新中枢的形成，一般来说，这种顶分型，成为真正顶的可能性很小，绝大多数都是中继的。例如，上海日线9月17、18、19这三根K线组成的顶分型结构。
>
> ![教你炒股票82：分型结构的心理因素](memoWX_019_Chan_fenxing/lesson082-image001.jpg)
>
> 但，**如果第二根K线是长上影甚至就是直接的长阴，而第三根K线不能以阳线收在第二根K线区间的一半之上，那么该顶分型的力度就比较大，最终要延续成笔的可能性就极大了。**例如上海日线6月18、19、20、21，里面有一个包含关系，但这包含关系是直接把阳线以长阴线吃掉，是最坏的一种包含关系。
>
> 一般来说，非包含关系处理后的顶分型中，第三根K线如果跌破第一根K线的底而且不能高收到第一根K线区间的一半之上，属于最弱的一种，也就是说这顶分型有着较强的杀伤力。例如上海日线5月28、29、30。
>
> ![教你炒股票82：分型结构的心理因素](memoWX_019_Chan_fenxing/lesson082-image002.jpg)
>
> **注：上涨中底分能否延续成笔观察分型3元素反之。**
>
> 分型形成后，无非两种结构：一、成为中继型的，最终不延续成笔；二、延续成笔。对于后一种，那是最理想的，例如在日线上操作完，就等着相反的分型出来再操作了，中间可以去宠幸别的面首，这是效率最高的。而对于第一种情况，前面说过，可以看是否有效突破5周期的均线，例如对日线上的顶分型，是否有效跌破5日均线，就是一个判断顶分型类似走势很好的操作依据。
>
> 不过，还有更精确简单的，就是这分型所对应的小级别中枢里，是否出现第三类买卖点，而且其后是否出现中枢移动。例如，对于一个顶分型，该顶分型成立后，对于该分型区间在小级别里一定形成某级别的中枢，选择其中最大一个，例如日顶分型后，可以找到相应的5、1分钟中枢，一般最大的就是5分钟，30分钟没可能，因为时间不够。如果该5分钟中枢或1分钟中枢出现第三类卖点，并该卖点不形成中枢扩张的情形，那么几乎100%可以肯定，一定在日线上要出现笔了。
>
> 可以100%肯定的，要不出现笔并最终有效破坏该顶分型，那一定要出现某级别的第三类买点，否则就算有短时间的新高，也一定是假突破。所以结合小级别的中枢判断，顶分型是否延伸为笔，是可以当下一目了然的。

### A.7 — 第69课：原始分型与用于笔的有效端点、当下修订

第二次检索补入正文25–37行的连续原例：同一几何顶／底能被识别，不等于它最终被选为笔端点。保留月线适用性、两个约束、取舍的反证过程和当下修订语境，不能只摘“完成后不改”一句当作程序稳定性保证。[7]

> 分型、笔、线段，在1分钟图上可以分辨，在月线图上的道理是一样的。但用月线图分辨，等于用一个精度超低的显微镜，只能看一个大概，但这个大概，却是最实质性的，是一个大方向。
>
> 下面，就是上海指数的月线图。绿箭头指着的是顶分型，红箭头的是底分型。打“X”的就是该分型不符合笔所要求分型的规范。这里，只要是两条：一、顶和底之间没有至少一K线；二、不满足顶必须接着底、或底必须接着顶。
>
> ![](memoWX_019_Chan_fenxing/lesson069-image001.jpg)
>
> 例如，第一个红箭头和第二个绿箭头之间显然不能构成一笔，也就是说，这两个，只能取一个：如果取第一个红箭头，那么第二个绿箭头就不是笔中分型，那么第二个红箭头，显然是一个底分型，因此，就形成两个底分型连续的划分，显然，这时候，第一个就不算了，这和前面说取第一个红箭头对着的底分型矛盾。所以，这里，只能取第二个绿箭头，这时候，第一个绿箭头对应的顶分型，自然就不算笔中的顶了。
>
> 后面的各分型，带“X”的，都可以按照上面两个原则去分析。
>
> 有人可能要问，这样分型的确定，在当下如何完成？这必须当下去完成。例如，当走势走到第一个红箭头时，显然，第一绿箭头的顶分型也可以暂时看成是确定的顶分型。但当第二绿箭头走出来后，这个问题就有了可修改的地方。
>
> 有人可能要疑问，这样分型是否随时可以修改？答案是否定的。一旦完成的图形，这修改就不可能了。分型可修改，证明图形没完成。例如，当第二个红尖头分型出现后，前面三个的分型的取舍就是唯一的。这个分型的可修改性，反而是一个对走势判断极为有利的性质，例如，第二个绿箭头走出来后，这图形未完成的性质就是百分百确定了，但所有图形必然完成，走势必完美。如何才能完美，这样，在理论的框架下，只有极少的可能，而这些可能，就成为综合判断的关键条件。然后根据各级别图形的未完成性质，就可以使得走势的边界条件极端的明确与狭小，这对具体操作，就是极为有利的。注意，这可和概率无关，是百分百的纯理论保证，最终所依据的，就是在本ID理论最早反复强调的走势必完美原则。

图像核对：整理本原图069/image001.jpg可见红／绿箭头、X及1／2标记，未以日线示意替代月线原例；未认证各附加标注的首发归属。该段说明的是作者在笔的有效分型取舍中的完成／未完成，不把它改写成“原始三根候选以后永不失效”。CC原始检测器与笔层是否等价于这段论证，仍须按各自输入、取舍与确认约定核对。

## Appendix B — Notes from CC's implementation

### B.1 — 代码版本、输入与本层边界

本次主要依据实际CC仓库的只读快照：HEAD `374268381a3eaeee4d220e67d63364b3907405f4`，2026-11-09复制，捕获时工作区clean；哈希与原路径在快照清单。[8] 这与既存网站旧版本`b1348795…`分开保存，没有把网站说明或注释当作运行证据，也未导入、执行CC代码。

可执行入口是`detect_fenxings(merged)`（fenxing.py:26–62）。它接收已消除包含的有序合并单元列表，输出**所有原始顶／底分型候选**；不做成笔距离、同型取舍、有效端点或买卖点判断。[9] 这一区分来自实际循环：满足条件便直接`append`，不查看上一条输出。因此候选窗口可以重叠；与A.4关于最终有效结构的结合律要求不是同一输出层次。

该函数没有校验输入排序、周期一致、OHLC合法性或确已去包含；这些是调用链的前提。少于3个单元时循环为空，直接返回空列表。不能把空列表一概解释为“数据已足够且市场没有转折”。

### B.2 — 三根比较与记录构造

1. 只遍历中心下标`i=1…len(merged)-2`，取`a=merged[i-1]、b=merged[i]、c=merged[i+1]`；两端没有完整窗口，不产生候选（26–30行）。
2. 顶要求`b.high>a.high`、`b.high>c.high`、`b.low>a.low`、`b.low>c.low`全部成立；底同时反向严格比较四项。四项之一相等即不能走该分支。两种都不成立便跳过（31–38行）。这是CC明确使用严格比较的实现事实；A.3说明有效去包含序列中通常不应留下相邻等边。
3. 输出的`index`是**中心合并单元下标**，`timestamp=b.start_ts`是中心代表时间，不是右侧出现后的确认时间。该对象没有另存`confirmed_at`字段（51–60行；models.py:146–161）。[9][10]
4. `high=max(a.high,b.high,c.high)`、`low=min(a.low,b.low,c.low)`是整个三根窗口的外包络。顶的high等于中心高点，但low通常不是中心low；底则low等于中心低点，high通常不是中心high。不能把两字段误读成中心K线自己的价格范围。
5. `trace`保存算法卡、顶／底rule ID、**含两端**的合并范围`[i-1,i+1]`和`a.start_ts…c.end_ts`原始来源时间包络。稳定显示ID为`fx-{timestamp}`，不是本项目memo009拟议的整数ID方案。[9][10]

这是一遍纯函数扫描，没有持久候选或回退栈。同型候选不被去重，也没有“前一个顶已经确认就永不改变”的承诺。

### B.5 — 补充核对：helper 输入前提与价格精度

`detect_fenxings()`没有配置参数；四项比较直接使用输入high/low，没有取整、容差、5周期均线或最小跳动单位分支。作者在第64课的精度说明见[memo020附录A.6](memoWX_020_Chan_bi.md)：一致精度是数据解释前提，不等于CC已经自动采用0.5点容差。若调用者预先量化价格，应对完整来源序列统一处理，不能只为了一个候选临时改比较精度；这不是本批新增的TDS默认方案。

同样，函数只按列表位置取相邻三根，不按时间重新排序，也不确认输入high/low均为有限数、来源区间正确或上游已去包含。正常引擎提供这些前提；手工直接调用helper的坏数据结果，不能反过来当作作者定义的反例。尾部价格修订后原始候选能消失，笔层有效端点还可能因新候选重新取舍；这两个变化不能用同一个“已确认”标签混淆。[9][11]
