## 1. 主要目标

- 财务目标：
	- 不亏钱为第一目标 
	- 高风险盈利 
	- 低风险盈利
- 产出： 
	- 交易推荐，历史交易记录 和 量化文章 
	- AI教育教岸 （针对1-3 4-6 6-9 9-12 的j金融AI十讲，讲座材料） 
	- 交易小游戏 （app IoC）

## 2. 项目原则

- 实事求是 解放思想
- Github + Codex + OOP + 记录
- 项目初期以抄为主，文件结构抄Github明星项目，类设计以抄为主，交易策略也已抄成熟明星的策略为主
- 技术和基础分析相结合，清晰知道赚钱和亏钱逻辑
## 3. 项目最终图像

- 幻方的网页
- 可扩展的构架
- 百花争鸣的算法和思路
- 有趣的美学界面
- 清晰文件的商业化路径
- 平衡中庸的视野

- AI的时代到来让技术平权： 隐学的交易策略 和 晦涩的数学 不再遥不可及
- 认真工作的团队迫切期待通过新质生产力实现自己的社会价值的驱动力
- 万事万物本就互联，在高维世界联系起来的线在新时代被将被AI平权

### 5.1 提问
- env 
	- five people team; engineers; all know cpp and python; 2-5 year experience
	- github repo
	- know at least five plus people who have 10+ yr trading experience and all claim they have their own winning strategies. 
	- have a access to various data source 
	- relatively fluent in vibe coding 
	- spread out in US and China 
- objectives
	- agile programming to test
	- documents and codes needs to be easy for new team members to catch up 
	- while oop is highest thinking; certain features could be implement with other forms with good capsulation.   
	- The code needs to have clear boundary 
	- when there is a new trading paper, we want to be able to test with an agent
	- when there is a new AI algorithm, we want to be able to test with an agent
	- when there is a new idea of visualize data, we want to be able to test it fast 
	- when there is a new gaming idea, we want to be able to create gaming skin to it 
	- perhaps not for trading within a minutes, minimal hourly and daily and weekly
	- when there is a new human trader say he has a new strategy, we want to be able to test it and create report
	- when there are thousands traders say they have different strategies, we want to be able to simulate it. 
	- Stock is the game of humans'; Stock is the game of agents: Technical and fundament shall have the two sides of the same game under behavior finance and fuzzy logic. 
	- use the third-party source code as much as possible
- Questions: 
	- could you scan most popular repos in different industry and suggest a folder structure that at least support the project up to 200 k lines of codes. 
	- just folder structure with justification

## 6. 项目执行的各阶段规划和目标
### 6.1 总论

代码库需要分级小步走 尽快做闭环再有机生长 快测看结果
## 7. 第一阶段 最小闭环 - 预热

### 7.1 初始化项目仓库
- 设置 repo
- 编写 AGENTS.md
- 编写 plan.md
- 确定目录结构和协作规则

### 7.2 读取柯 CSV 数据
- 读取柯提供的 CSV/OHLCV 数据
- 转成统一 Kline 数据结构
- 做最小数据校验

### 7.3 最小可视化
- 画出原始 K 线或收盘价曲线
- 确认时间轴、价格轴、成交量没有错误
- 输出一张可复现图

### A.7 OOP Note
In `cc`, you should not imagine the backend as one big OOP hierarchy. It is more like modular Python. Some parts are object-oriented, but many parts are function-oriented.

A class is used when something owns state or a resource. For example, `DuckDBKlineRepository` owns the DuckDB connection. `TqsdkAdapter` owns the connection to a market data source. `EngineRegistry` owns and manages analysis engine instances. These things make sense as objects because they remember state across calls.

Algorithm code is often not like that. A Chanlun function may take K-lines or lower-level structures as input, compute something, and return structures. That is closer to scientific computing: data in, transformation, data out. It does not always need to be wrapped in a class.

FastAPI route files are also mostly function-oriented. A URL request comes in, FastAPI finds the route function, and that function coordinates the work. It may call repository methods, data adapters, algorithm functions, serializers, and then return JSON.

So the style is mixed. Use OOP where there is ownership or long-lived state. Use functions where there is computation. Use dataclasses or Pydantic models where you need structured records. That is the practical design style of this repo.

## Appendix B: 缠论画图
Raw CSV has OHLCV rows.

Each row becomes one Python `Kline`.

`ChanEngine` receives all `Kline` objects.

Engine validates timestamp and prices.

Engine stores raw K-lines.

Engine performs 包含合并.

Contained candles are merged into structural K-lines.

Merged K-lines keep original start/end indexes.

Engine scans merged K-lines three at a time.

Middle higher than both sides becomes 顶分型.

Middle lower than both sides becomes 底分型.

Engine scans 分型 in time order.

Opposite 分型 can become a 笔.

Same-type 分型 cannot directly form a 笔.

Candidate 笔 must be far enough.

Default distance is merged index difference at least 4.

Gap can count as extra distance.

Candidate 笔 must pass endpoint validity.

Candidate 笔 endpoint must be true interval extreme.

Valid 分型 pair becomes a blue `Bi`.

Many `Bi` objects form the lower-level stroke sequence.

Engine uses `Bi` sequence to build `线段`.

A `线段` is a larger swing made from multiple `Bi`.

The fifth graph uses `线段`, not raw candles directly.

Engine uses `线段` to find `段中枢`.

`段中枢` means overlapping price zone among segment movements.

Each blue rectangle is one `段中枢`.

`ZS1`, `ZS2`, etc. label these centers.

Engine uses segment centers to build `L1 走势`.

`L1 走势` describes the larger market movement.

Purple lines are segments inside the latest L1 structure.

Orange lines are later segments after the current L1 endpoint.

Gray pale line is the original close-price path.

Blue rectangles are segment-level centers.

Thick dashed line summarizes the larger L1 movement.

Vertical dotted line marks the current L1 endpoint.

Top horizontal bar marks the life span of the latest L1 structure.

So the fifth graph is: raw price background plus L1 structure computed from segments and centers.
