# memo0034_memoguidance

## 0. 范围与原则

### 0.a 当前写作指南

**Memo要让读者看懂问题、判断依据和下一步，不依赖聊天记录再解释。** 本篇是[memo0003](memo0003_memoguidance.md)的更新版，吸收0032、0033及此前算法笔记的修改经验，作为后续memo写作指南；0003保留为历史稿。[^basis]

[decision] 保留旧版的紧凑笔记、稳定编号、来源和执行记录规则；更新其章节与工作流模板。普通知识memo按问题组织，长算法memo可采用0032的结构，不强制每篇套同一目录。

### 0.b 最重要的变化

- **先讲判断目的：** 要识别什么、保留什么，再讲条件和操作。
- **按领域问题分步：** 如“原笔延伸还是反向成笔”；配置、初始化、返回对象放实现对照。
- **简洁保留精度：** 删重复与套话，保留条件、图、例子、等号、失败出口和必要限制。
- **原文优先：** 原文连同前提、上下文和后续澄清，是解释原理论的依据；树图、网站和代码不能替代它。原文、推论、参考实现与项目变体分别标明。
- **修改成套完成：** 正文、树、图、编号和跳转同步；旧稿与原始资料按授权保留。

## 1. 写给人看：先让判断有意义

### 1.a 一步回答一个问题

先用一句话说清这一判断的目的，再用具体对象展开。读者只看标题，应能看出问题如何向前推进。

**0033的修改例：** “初始化列表 → 遍历分型 → 调用标准检查”改为“寻找第一笔 → 判断原笔是否延伸 → 判断反向能否成笔”。前一种适合实现说明；正文用后一种组织，再用代码核对它是否准确。

同样，解释类时先说它负责什么、调用者给什么、得到什么，再列成员和方法。解释研究结论时保留机制、假设、限制与项目影响；简短不等于把复杂内容写浅。

### 1.b 先定义，再比较

术语首次出现时用完整句子定义，随后保持同一含义。定义要指出对象及来源；“X：执行某操作”通常没有解释X是什么。

- **准确的短定义：** 0032中的“续笔”指前面已有线段，从前段终点接着判断下一段。
- **会改变理解的省略：** 只写“不是第一笔”，丢失了已有前段这一前提。
- **比较前说清范围：** “缺口”究竟指原始K线、合并区间还是特征元素的价格分离；不能只写“有缺口”。

使用A、D等已定义点名，少用含糊的“这个点”“后面那个”。符号辅助说明谁固定、谁移动，不代替说明。

### 1.c 真正的mental model

**Mental model是对判断目的和对象关系的简短解释。** 例如：“先假设D是转折点，再整理判断依据，最后验证或否定假设。”这比重复方法名更有帮助。

它不能引入代码没有测量的“信息价值”等评分，也不能替代精确条件。详细讨论放本步之后或讨论章；决定分支的前提仍留在正文。用户说“特征元素用于判断”，不等于要求把它从判断图中删掉。

### 1.d 紧凑但有语法

短段落、短列表、必要的空行即可。保留主语和动作，明确“谁和谁比、改什么、去哪里”。普通内容不用层层引用框，也不必每句话带标签。

保留有用的`[concept]`、`[decision]`、`[source]`、`[evidence]`、`[example]`、`[project consequence]`等标签；没有新作用的标签可以省略。默认不用YAML或长元数据头。用户要求去掉元数据时，不自动删除有阅读作用的标签。

## 2. 结构：总览与逐步展开

### 2.a 普通知识memo

一篇解决一个可复用问题，包含问题、结论、依据、例子及项目影响；有未决处就写明。它们不必各占一章。保留用户已有的讲解顺序，采用能讲清内容的最小结构。

0003中的七章目录和逐项`System／Path／Verify`是可选工具，不再作为通用骨架。安装、配置和命令操作仍可写环境、路径与验证结果；价格判断无需重复这些栏目。

### 2.b 长算法memo的参考结构

```text
0. 范围与方法
   0.a 范围；0.b 方法；0.c 最终树＋约300字总结
1. 原文与依据
2. 共同推导／主体流程
   2.0 样图与符号
   2.1 S1初始条件
   2.2及以后：扩展树、判断目的、分支与例图
3. 补充讨论与实现对照
4. 参考
附录：按需要保留原始资料或参考代码
```

这是0032、0033形成的写法，不要求简单memo也放树或300字总结。总结应贯穿主问题、判断顺序、对象变化和主要限制，不逐条复述目录。

### 2.c 一个分支怎么写

```text
小节标题：2.4.b. 分支S4.b ＋ 本支问题
图：当前对象、条件和变化
条件：何时走此支。
例子：沿用主例的具体价格或输入。
处理：保留什么、改变什么、下一步编号。
```

这是短分支的常用顺序。复杂检查先交代固定对象与比较顺序，再分支；分型不足、相等或尚未展开的规则，在相关出口旁简短说明。不要为统一格式给简单分流步骤增加无用栏目。

### 2.d 照范文，要读当前范文

用户说“按2.4来”或“不够0032”时，先读磁盘上的现稿，对照标题、树、图的位置、段落次序、记号和例子形状。只改标题，或套上同样编号，不能复现讲解方式。

复用格式不等于复制业务条件；笔与线段的完成条件不同，不能把一个主题的“确认终点”直接移植到另一个主题。

## 3. 树与编号：保持同一条推导链

### 3.a 从原根扩展

沿用`├──`、`│`、`└──`的目录树。新增小节不产生新根，节点父子关系由已经同意的判断关系决定。

```text
2.1中的树：                 2.2中的树：
S1 初始条件                 S1 初始条件
                           ├── S2.a 条件成立 → 后续步骤
                           └── S2.b 条件不成立 → 指定处理
```

不在S1与S2.a之间擅自插入一个S2包装层。几何情况不同，但对象变化和下一操作相同，可以共用分支；只因标签不同就分叉，会让树机械膨胀。合并分支前仍须核对条件与实际出口。

### 3.b 保留每一步的树

2.1保留初始树，2.2在它基础上扩展，后续照此推进。最后一节保留完整树，并复制到0.c；不能为“整理”而删除前面快照。共同规则有修改时，同步所有包含该节点的树，但不把未来节点塞进早期快照。

章节、S编号和分支字母一一对应。某步骤被多条路径调用，应写明各自的成功／失败出口；回S2还是S2.b必须准确。

### 3.c 编号修改的边界

用户只要求重新编号时，只改编号和相应引用，保留原文条件、例子、图与附录。拆分分支后逐项检查：标题、各树、正文跳转、图注、图内文字、文件名和链接。

**例：** 原S7.a拆成a、b，原b、c顺延为c、d；图内仍写旧S7.b就没有改完。PNG中的文字须从绘图脚本重画，仅改Markdown说明不够。

## 4. 例子与图：让读者能复现判断

### 4.a 固定主例，变化明说

主例贯穿各步，点名、价格、时间次序一致。0033沿用`A20→B8→C17→D6→E19`；镜像、截断输入、开启强势和局部给定状态分别标为独立例子。

成功例说明为什么通过；失败例说明失败后试什么。不能用一组只满足局部比较的点，声称它已通过真实入口。镜像例也要重算上下关系和等号，不能只翻图。

### 4.b 图里有哪些对象

先画判断涉及的价格关系，再用颜色、实线或虚线标注角色，并给出图例：

- **原始记录：** K线、笔及实际输入，不因候选失效而消失。
- **判断对象：** 包含处理后的区间、虚拟特征元素等，由原始记录派生。
- **当前画法：** 已接受的连接、待查候选及旧画法；三者不能混成同一条实线。

“虚拟”说明它是判断对象，不是行情新增加了一根笔；需要解释它时仍应入图。灰线若只连接分型，标明“连接示意”，不能让读者误认逐笔成交路径。

有前段才叫续段时，图上必须画出前段。初始条件图是后文的共同参照，不随目录调整被删掉。流程框可补充操作顺序，价格结构应由价格图说明。

### 4.c 合并必须展示前后

给出方向依据、输入区间、合并结果、不变的参照及保留的原始记录。后续判断使用新值，重新检查受其影响的缺口等关系。

**独立数值例：** 假设本轮已经确定按向上规则合并，固定参照区间为`[100,120]`。

```text
合并前：X=[110,130]，包含Y=[123,128]；X与参照重叠于[110,120]
向上规则：新低点取较高者，新高点也取较高者
合并后：X'=[max(110,123), max(130,128)]=[123,130]
重新比较：X'与[100,120]分离，120与123之间出现缺口
保留：X、Y的原始记录；变化的是判断区间
```

这只演示区间变化，不证明某个完整算法会进入此状态。不能从被合并元素本身的方向，猜测应采用哪种合并方向。

### 4.d 画完还要看

先算条件与结果，再生成图；逐图打开检查文字遮挡、点位、比例、编号、线型和主例一致性。失败、平价、镜像与前后变化按需要画，不必把所有分支都扩成流程海报。图与正文不一致时一起修正，不能在后文补一句免责说明就算完成。

## 5. 推导：理论、代码与判断出口

### 5.a 分清依据的身份

**[decision] Memo必须尊重原文。** 解释原理论时，先核对作者的定义、适用前提、例外和后续澄清，再组织正文、树图和算法。复现KWX行为时，网页与代码是实现证据；实现与原文不一致，应明确记录差异，不能反过来修改原文的含义。

- **原文引用：** 保持原句，标明出处；转述明确为概括。
- **理论解释：** 说明由哪些前提推出，区分必要与充分条件。
- **参考代码：** 核对实际比较、对象修改和调用方，不只相信注释或方法名。
- **项目规则：** 标明已决定、提议或未决；偏离原文的选择必须明确标为项目变体。用户确认树形、文字或出口，不等于确认偏离原文；参考代码存在某功能，也不等于项目已采用。

0033的强势与反弹修正因此标为参考扩展。解释先依领域概念组织，再用价格算例和代码核对；既不把代码行为冒充原文，也不为了贴近理论而隐去实现差异。

### 5.b 先推前提，再增加判断

新条件出现前，检查前面已经保证了什么。若结论在特定入口下已被保证，说明推导及适用范围，不再造一个独立关卡；不能把这个局部结论推广到所有入口，也不能顺手删除代码中的防御检查。

用户提出结论时先检查推理，不能为了顺着说而暗中补前提。发现旧结论错误，纠正那句话和依赖它的图、分支；不要留下原结论再附相反的补充。

不能把必要条件、简单例子或局部检查升级成所有输入的拒绝门槛。例如，“第三笔尚未达到当前区间的方向极值”不能直接推出“原起点以后不能形成线段”。发现依据不足时，在主步骤撤回已核实的表述，写清待核对条件及影响；不能仅在附注中将问题称为“允许不同的算法”。尚未推导出替代规则时，保留旧稿作为待校准记录，不补造新出口。

### 5.c 每个出口都能继续走

读者应能在纸上确定：当前对象、固定参照、比较、变化后的状态，以及下一步。

- 写“突破D”时，明确比较哪个端点与D、向上还是向下、是否包含相等。
- 写“继续”时，明确下一旧候选、下一输入分型、下一笔或补齐的数据。
- 分开成功、明确失败与数据不足；缺规则则写明未决对象，不临时补规则凑完整。
- 保留等号、空输入、选项关闭、输入耗尽等适用出口。辅助检查失败，不等于整个计算结束。
- 分流步骤只决定去哪里，下游比较放实际执行处，避免让人以为同一判断做两次。

**修改例：** “失败后继续”可改为“保留起点，瞬移终点，重复S4”；若新终点的选择规则尚未定义，还要明确写出这个缺口，不能把这句话当完整算法。

### 5.d 搜索次序与覆盖范围

循环要写清集合、顺序、固定对象和移动对象。先找“第一条标准成立的参照”，再比振幅，不等于找“第一条振幅有利的参照”。首个决定性事件优先，不能跳过失败证据等后面有利的点。

**0033首笔例：** 固定当前分型，先试最早旧候选，再试下一旧候选；全部失败才读下一输入。两个“下一”不同，候选失败也不删除原始数据。

分段或分组还要说明首个候选失败怎么办、前缀能否未分配、组间是否连续、尾部未完成如何保留。不能由“开头可未覆盖”推成“中间也可留洞”。

### 5.e 端点位置不等于证据时间

区分原始输入、内部候选、搜索位置、已接受结果和显示用的临时线。临时线不证明程序已选中该候选；确认标记也须查明是否真的冻结结果。

说明一次调用保留什么、下一轮推进什么，以及新增数据后是接续还是重算。0033扫描到D时可以借用整份输入中已有的E；真实数据只到D时，不能声称已获得E的许可。时点复盘应从当时原始数据重新推导，不能只裁切最终成图。

## 6. 修改与验证：把反馈写回文稿

### 6.a 按用户当前要求推进

“先加标题”“先复制树”只做这一层，不提前发明未讨论的规则。已经授权的修改直接完成；指定保留原文时，重编号不能附带改写内容。

用户说“没懂”“漏了对象”或“太机械”，应重读相邻步骤，重写整个受影响的解释。采用用户准确、简练的说法作为正文主线，不把它埋在补充说明里。检查全篇同一问题，别只修聊天中举到的一处。

### 6.b 先保留，再改到位

新理解通常写进后续memo，并链接旧稿；不为统一思想追改历史稿。复制章节、原始代码或用户文字时按要求保留内容；来源中的错误可以旁注，不暗中修正原文。

术语变化同时检查标题、树、正文、图注和图内文字。改图、删除图、移动图是不同动作；补充概念解释不自动授权删图。用户要求恢复旧图时，核对恢复的版本与当前文字一致。

### 6.c 验证声明要匹配证据

| 做过的检查 | 能支持什么 | 不能代替什么 |
|---|---|---|
| 来源与调用流程审读 | 分支、顺序及修改对象的对照 | 实际运行 |
| 数值或局部条件检查 | 给定输入的比较结果 | 状态从入口可达 |
| 人工设置中间状态 | 该状态下的处理 | 真正进入该状态的过程 |
| 真实入口运行 | 这组输入的中间状态与输出 | 全部输入及配置的正确性 |
| 图片目视检查 | 可读性及图文呈现 | 规则正确性 |
| 从文稿独立编写验证程序 | 已覆盖范围内的规格可执行性 | 一般性证明或生产就绪 |

声称“实现就绪并已验证”前，须从文稿走通初始化、状态转移、失败与终止到输出，运行必要的最小验证，并把覆盖范围对应到文档步骤。不能直接抄参考实现后宣称新文稿已独立验证。发现缺规则先修文稿，不为让测试通过而补假设。

**分支闭合、程序可执行和符合原文是三个不同结论。** 测试通过只支持已检查输入下的执行行为；符合原文还须逐步核对定义、前提与推导，不能由树图完整或测试数量代替。

讨论稿或未授权实现时，不因此扩展为开发任务；如实写“未进行完整可执行验证”。有限例子、渲染断言、已有单元测试分别记录，不混合计数。文档编辑只做相关核对，不为格式修改编造测试需求。

## 7. 继承的项目约定

### 7.a 文件、编号与历史

- 目录为`docs/memo/`；文件名为`memo`＋四位数字＋`_`＋简短主题＋`.md`，例如`memo0034_memoguidance.md`。
- 编号是稳定标识，不为填空号重排。`memo0013`、`memo0014`仍按2026-08-31的用户决定保留为空；新跳号在本指南、下一篇memo和master log记录原因。
- 新主题名一般使用小写英文；迁入的原始笔记保留其命名决定。以单个类或紧密类族为主题时，用`memo000N_class_name.md`。
- 改名同步AGENTS、README、plan、status、阶段文档及其他有效引用；历史事件记录不伪装成新事件。
- `kb/`保持退役；不另建重复知识库。0003中提出的memo索引只是旧开放问题，不因本次更新自动创建非编号文件。

### 7.b 不同类型的memo

- **类设计：** 先写职责、输入输出和使用例，再分成员、方法、边界与验证；例如领域对象是否禁止直接读写文件。
- **论文评论：** 逐篇写，标题下放AMA格式引文，再谈论点、机制、证据与项目影响。默认不强制对比表、论文序号或每句标签；仅在用户要求排名或高被引依据时加入引用量证据。
- **研究总结：** 压缩主张、因果机制、建模假设、矛盾和可检验推论，保留概念深度。
- **操作笔记：** 命令放操作或执行段，说明路径、关键环境和成功标准；执行记录写实际观察，不能把预期结果当已运行结果。

### 7.c 来源与记录各归其位

正文用紧凑引用，来源日期、版本、校验和及源码行号放脚注或参考区。影响结论的假设与限制仍放在结论旁。图、脚本和完整数据按项目目录存放，memo链接它们。

不保存密钥、密码、账户信息、私有行情、大型原始数据或大型生成物；示例使用明显占位值。修改用户资料前先读当前文件；原始引文、附录和历史稿需要保留时，核对实际内容未变。

Memo保存可复用知识；执行总结保存改了什么、运行什么、结果和限制；master log记录带分钟时间的项目进展。与当前里程碑有关的工作同步阶段文档、plan和status。讨论写作不自动成为实施授权，已有授权也不逐项重复索取。
